# EmbeddingGemma 2 experiments

| Experiment | Decision / evidence |
| --- | --- |
| Float32 residual stream, BF16 matrix inputs | Retained.  Its worst probe has cosine 0.999985 to the float32 reference, while Hugging Face BF16 has 0.999867. |
| Fused QKV and gate/up projections | Retained.  Each pair of projections that share an activation runs as one GEMM. |
| BF16 safetensors only | Retained.  The text backbone is 540 MB and 268 MB of that is the token table, which is a row lookup, so quantizing saves little memory or time.  GGUF quants wait for published quality measurements in [discussion 478](https://github.com/gufo-org/gufo/discussions/478). |
| Lazy vision tower | Retained. Text startup uploads only the text backbone. The first image request loads the 16-layer vision tower and projector; later requests reuse them. Audio tensors remain unindexed until an audio request loads its own tower. |
| hipBLASLt instead of hipBLAS | Retained.  hipBLAS has no matrix-core kernel for this BF16-in, float32-out transposed GEMM and runs at 4.5 to 5 TFLOPS in `gemm_bench_hip_test`, while hipBLASLt reaches 17 to 27 TFLOPS at 1,024 rows.  No fixed heuristic rank wins across shapes, because the best rank moves between 4 and 8, so Gufo times each shape and row bucket once at load.  Against #700 over HTTP, a 404-token request drops from 41.4 ms to 20.5 ms, which is 2.0 times faster.  Concurrent single-input requests of 404 tokens are 2.0 to 2.1 times faster, and batches of 8 and 32 inputs are 2.2 to 2.3 times faster.  A request of about 8,000 tokens is 1.3 times faster, and load time grows from 0.53 s to 2.2 s. |
| Row-chunked GEMM and consumer | Retained.  Chunks of 1,024 rows bound the float32 scratch buffers.  Unchunked, the gate/up buffer for 8,192 tokens would be 8,192 x 4,096 x 4 bytes = 134 MB and the QKV buffer about 100 MB. |
| Matrix-core attention | Retained.  WMMA flash attention, with four waves per 16-query tile splitting the head width, replaced a VALU kernel.  Each layer transposes the values once, so a lane reads 16 consecutive keys of one column.  Against main with the hipBLASLt GEMMs, a 404-token request drops from 19.95 ms to 12.94 ms, which is 1.54 times faster.  A request of 1,940 tokens is 2.35 times faster and one of 8,072 tokens is 4.83 times faster, while a 40-token request is unchanged at 1.02 times.  Batches of 8 and 32 inputs are 1.57 and 1.77 times faster, and concurrent requests of 404 tokens are 1.60 to 1.61 times faster.  Image requests change by about 1 percent, because the vision tower takes most of their time. |
| Precomputed rotary tables | Retained.  Double-precision cos/sin tables per position replace per-element `powf` and `sincosf`. |
| Device turns per batch | Retained.  One lock held for a whole request made a one-word request wait 58.4 s behind 32 inputs of 8,000 tokens.  With arrival-order turns per device batch it waits 1.01 s, and the long request still takes 59.5 s.  A plain mutex is not enough, because the releasing thread can take it straight back. |
| Unmapping the checkpoint after upload | Retained.  Keeping the mapping held 656 MB of file-backed RSS that nothing reads after the upload.  RSS after load falls from 930 MB to 286 MB. |
| Cross-request batching | Retained.  Text requests that wait for the device share a batch of up to 8,192 tokens, oldest first, and a lone request runs at once.  The request at the front of the queue runs the batch for itself and the requests behind it, so there is no device thread.  A request that fits in one batch is never split.  A larger request keeps the per-batch turns of the row above.  A request with images runs in a batch of its own, in arrival order, as the next row explains.  Against main 194db882 on gfx1151, sixteen concurrent 40-token requests take 27.16 ms at the median instead of 95.96 ms, which is 3.53 times faster.  Sixteen concurrent requests of 404 tokens are 1.21 times faster, four are 1.05 times faster, and the concurrent rows of 8 inputs are about 1.03 times faster.  Single-client rows are within 1.3 percent of main, and image-only rows are unchanged.  In a mixed load of 16 clients that alternate image and text requests, the medians improve by 3 percent for images and 5.5 percent for text, but the image p95 is 8 percent higher, from 6,767.15 ms to 7,315.21 ms.  A run with image and text requests on separate threads shows no such rise, and its image median, p95, and mean match main or are slightly lower.  Text requests queued behind images wait about 4 s on both builds, because each image takes about 560 ms and the queue is first come, first served. |
| Image requests in their own batch | Retained.  A request with images runs in a batch of its own, in arrival order, and never shares a batch with a text request or another image request, so the first image request loads the vision tower in its own batch.  Packing images into shared batches gained nothing and slowed text on gfx1151.  The vision tower runs once per image and takes most of the time, so 16 concurrent image clients ran at 481 tokens/s on main and 484 tokens/s with shared batches.  With 16 clients that interleaved image requests and 16-word text requests, the text median rose from 4,105 ms on main to 4,454 ms, which is 8.5 percent slower, and both passes of the shared-batch build were above both passes of main.  The text p95 of the shared-batch build fell from 5,630 ms to 4,462 ms, because every text request then waited for one image batch instead of a variable number.  The median is what most requests see, so image requests stay out of shared batches.  Text-only requests still gain from shared batches, up to 3.53 times at 16 clients of 16 words. |
| Server does not add task prefixes | Retained as the default.  The OpenAI API has no task parameter, so clients choose the prefix.  `prompt_name` and `--default-prompt-name` add a checkpoint prompt only when asked (#723). |
| Attention window radius 512 | Retained from the checkpoint configuration.  The model card's 1,024 is the full window width. |

| Reference image preprocessing | Retained. Uint8 antialiased bicubic resize rounds and saturates after each separable pass, with the same adaptive signed coefficient precision as Torch 2.12.0. Every resized patch byte matches the independent official processor fixtures, including extreme aspect ratios. |
| Vision padding removal | Retained. Only real patches run through the bidirectional vision encoder; reference padding keys are masked and pooled padding is discarded. Seven image/mixed-input probes retain cosine ≥0.9999 against official float32 outputs. |

| Audio implementation | Decision / evidence |
| --- | --- |
| Independent Gemma4 frontend | Retained. Semicausal periodic-Hann magnitude/HTK features match the pinned official extractor within 4.77e-7, with exact masks and counts. Whisper/ASR preprocessing is not substituted. |
| Lazy float32 audio tower and projector | Retained. BF16 checkpoint weights widen once; audio owns reusable bounded scratch and loads only when requested. Independent encoder/projector fixtures and ten final-vector probes pass. Isolated load allocation delta is 1.31 GiB; a one-second clip takes 146.9 ms including first load, then 28.3 and 27.8 ms. |
| Strict audio attention horizon | Retained from pinned code. Its mask uses distance < 12 despite a 13-position left-context configuration; including distance 12 failed the longer independent fixture and was corrected. |
