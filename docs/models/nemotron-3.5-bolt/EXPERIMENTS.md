# Nemotron 3.5 Bolt 74B-A9B experiments

| Approach | Status |
| --- | --- |
| Support only NVIDIA's quantization-aware 24GB GGUF | Retained; three storage formats (IQ2_XXS, NVFP4, Q8_0) instead of the dozen mixed into community quantizations, and the variant NVIDIA's accuracy figures describe. |
| llama.cpp as the numerical reference | Retained; the BF16 checkpoint (about 148 GB) does not fit in 128 GiB, and llama.cpp runs the same GGUF. |
| Float32 activations and float64 accumulation in the CPU reference | Retained; it agrees with llama.cpp's Vulkan and CPU backends as closely as they agree with each other, without imitating either backend's activation quantization. |
| Judge reference differences against llama.cpp CPU vs Vulkan | Retained; a CPU control needs operation offload disabled (`llama_logits --cpu`), otherwise host-resident weights still run their batch matmuls on the GPU. |
| Compare the CPU reference on llama.cpp token IDs | Retained for the trunk; tokenization is checked separately because llama.cpp approximates the `pixtral` pre-tokenizer's Unicode case classes. |
| Split with exact Unicode categories, as Hugging Face tokenizers does | Retained; llama.cpp keeps a non-ASCII lowercase-to-uppercase change in one piece. On the 26-text golden corpus (scripts, marks, emoji, digits, code, whitespace, added tokens) Hugging Face, llama.cpp and Gufo produce identical token IDs. |
| Own F32 router GEMV for up to 8 tokens; hipBLAS SGEMM only for prefill | Retained; hipBLAS took about 210 µs per block for one token (8 ms per decoded token), the GEMV streams the 5.7 MB of router weights once. Decode 21 → 24 tok/s. |
| Capture the single-token step as a HIP graph per session | Retained; about 1,260 dispatches per token left the GPU idle about 20% of the time. Positions moved to device memory so the graph replays at every position. Greedy output unchanged. |
| Per-stream scratch arena for the matrix kernels instead of `hipMallocAsync` | Retained; removes per-call allocation and lets the decode step be captured. The arena is reserved when the session is created, because the first product may already run under capture. |
| Split decode attention (32 key ranges per head, then merge) | Superseded by the split over 64 blocks per KV head below; one workgroup per head had left a 2,600-token cache to 32 workgroups (decode at that depth 25.9 → 27.3 tok/s). |
| Stage B, C, dt and x in LDS per 32-token tile in the scan | Retained; the eight rows of a block share their head's inputs. The scan took 15% of a 2,622-token prefill before. |
| Query-tiled prefill attention (16 queries, 64-key K/V tiles in LDS) | Superseded by the FP16 WMMA flash attention below; it had replaced a per-query kernel that took 13% of a 2,622-token prefill (377 → 440 tok/s). |
| Cache boundary before the generation header | Retained; the template replaces earlier reasoning with `<think></think>`, so a follow-up turn diverged after the previous prompt's header. With the boundary a 1,023-token follow-up re-prefilled 35 tokens (TTFT 2,376 → 407 ms). |
| Verify a block without writing the Mamba states, keep the convolution and scan inputs, replay the kept prefix on commit | Retained; a partial commit is bit-identical to appending the kept tokens, and costs about 3 ms per round instead of per-token state copies (160 MiB each). |
| Inject only the last sliding window (1,024 + 8 positions) of a prompt into the drafter | Retained; drafts never read further back, so long prefills skip the drafter's projection for older rows. |
| MMVQ instead of tiled MMQ for IQ2_XXS experts up to 8 tokens (llama.cpp switches above 4 on RDNA3) | Rejected; verifying 8 tokens took 85.7 against 83.8 ms. Both paths dequantize per token and are compute-bound. |
| One weight-streaming kernel for the F32 router and the drafter's BF16 products: activations staged in LDS, a register copy per token reused over several rows, narrow matrices split across waves | Retained; the first version re-read the activations per row (40 GB/s on the drafter's 32 MB Q/O projections). Draft 18 → 11 ms; router for 8 tokens 156 → about 40 µs per block. |
| Time verification with 8 copies of one token | Rejected as a benchmark; identical tokens route to the same 9 experts. Distinct tokens verify in about 100 ms, not 68–80 ms. |
| Size the routed MMQ grid by tokens instead of tokens × slots | Superseded when the routed experts left MMQ (below); a token selects an expert at most once, and the grid had had 9× too many column tiles, about 3 ms per million empty workgroups (2,622 tokens 536 → 603 tok/s). |
| Prefill chunks of 2,048 instead of 512 tokens | Retained; at 512 tokens each of 240–496 experts saw about 10 of its 80-column tile. pp2048 runs as one chunk, matching the HTTP runner's 2,048-token step. |
| Scan with the state in registers: 4 rows × 8 lanes per thread for long chunks, 1 row × 2 lanes for up to 8 tokens; state-major layout, DPP lane sums, next tile prefetched | Retained; the 32-lane version reduced over LDS (`ds_bpermute`) 12 times per token and could not keep its 1,024 blocks resident. Prefill 20 → 2.6 ms per layer; decode 35 → 33 µs, now at the state's DRAM bandwidth. Two rows per thread with two lanes spilled 60 VGPRs. |
| IQ2_XXS vector kernel: BF16 grid table in LDS, signs by XOR, `v_dot2_f32_bf16` | Retained; llama.cpp's MMVQ read the grid from global memory at about 100 GB/s. Experts 8.0 → 5.7 ms per token. A lane takes a whole 32-value group when rows hold 4k super-blocks (264 contiguous bytes per wave step), else eight values. |
| Lane walk over flattened (row, block) pairs; eight rows per wave; register prefetch of the next super-block | Rejected; none beat the two layouts above (activations no longer shared by rows, or no change). |
| F32-activation dense vector kernels for NVFP4/Q8_0, also with an LDS decode table and unaligned 16-byte loads | Rejected; 152–205 GB/s for NVFP4 against MMVQ's 210–224 GB/s. MMVQ stays; its Q8_1 input now comes from the norm kernels. |
| Q8_1 written by RMSNorm, gated norm, slot sum and attention context; residual add fused into MMVQ (`x_bias`, one token) | Retained; 1,270 → 757 kernels per token, decode 33.9 → 35.2 tok/s, token-by-token vs bulk KL 3.6e-6. |
| Fold the NVFP4 output scale into the Q8_1 activations | Rejected; small scales pushed the FP16 block scale into subnormals (decode KL vs llama.cpp 3e-3, seven more top-1 flips on the long parity prompt). The scale is applied after the product (`dst_scale`). |
| Shared expert on a parallel branch of the decode graph | Retained; overlaps the router, top-k and routed experts, about 0.5 ms per token. rocprofv3 hangs on this graph; profile with the branch on the main stream. |
| NVFP4 prefill product on FP16 WMMA instead of Int8 MMQ | Retained; MMQ rescaled after every 16-value WMMA (18 TFLOP/s). FP16 decode is exact for E2M1 × UE4M3: ssm_in 16.9 → 11.1 ms, ssm_out 7.4 → 5.2 ms at 2,045 tokens. Blocks must share token tiles: weight-tile order reread the 67 MB of ssm_out activations per row tile (11.0 ms). pp2048 715 → 834 tok/s. |
| Flash attention on FP16 WMMA: a wave takes one query token's 16 heads of a KV head (one row tile, one causal limit), 8 tokens share 64-key K and transposed V tiles | Retained; the query-tiled F32 kernel ran at about 1.5 TFLOP/s and took 2.7 ms per new token at depth 32K. pp2048 at depth 32,768 257 → 613 tok/s; a 32K prompt 84 → 48 s. Q and P round to FP16 (output within 2e-4 of exact softmax). |
| Short chunks (decode, verification) split the keys over 64 blocks per KV head and merge | Retained; the old decode kernel read each KV head once per query head (16×). Decode at depth 32,768 28.6 → 32.1 tok/s, unchanged at short context. |
| Random draws from a device head per logits row (largest logit, F64 softmax sum, the tokens within 1/16-nat bins of the cut, at most 1,024) instead of host passes over the vocabulary | Retained; under GPU load the host sampler took about 2 ms per row at 140 W and 3.4 ms at 85 W (0.83 ms idle), several rows per draft round. At depth 32K sampled draft-and-verify 58–61 → 67.8 tok/s (code) and 50.7 → 58.3 (docs), autoregressive 33.9 → 34.9; greedy unchanged, seeded answers byte-identical. |
| IQ2_XXS vector kernel for several tokens: per grid entry, every row against the tokens' activations (one entry's slice in registers instead of four), half the staged super-blocks | Retained; the 8-token kernel held 8 tokens × 4 entries of activations (253 VGPRs, 5 waves per SIMD). The shared expert at 8 tokens 103 → 81 µs (up) and 85 → 73 µs (down) in isolation, sums in the same order. Draft-and-verify 110 → 113 tok/s (Fibonacci), 65.8 → 67.2 (depth 32K). |
| BF16 WMMA for the shared expert at 2–8 tokens (IQ2 decoded into A fragments, 4 row tiles per wave, columns split over the waves) | Rejected; gfx11 WMMA needs A in both half-waves, which doubles the decoding, and 8 tokens fill half of the 16 columns: 106–141 µs against 81 and 73 µs. Above 4 tokens the vector kernel is bound by its BF16 dot products (2 tokens 34 µs, 4 tokens 43 µs, 8 tokens 81 µs). |
| Routed IQ2_XXS prefill experts on BF16 WMMA instead of llama.cpp's routed MMQ: slots grouped by expert into tiles of up to 32 (one route per layer for up and down), a thread per weight row loading its 66-byte super-block once for eight groups, exact signed grid values in BF16, each group's two WMMA steps scaled in F32, ReLU² at the store | Retained; MMQ quantized and gathered the activations per slot, ran 80-column tiles over about 37 slots per expert and launched some 2×10⁵ mostly empty workgroups per call. Routed up and down per layer about 15.5 → 11.5 ms (15 TFLOP/s); pp2048 990 → 1,087 tok/s, at depth 32K 840 → 897. Exact weights and BF16 activations as in decode: bulk vs incremental KL 8e-5 → 7.4e-5. Staging the activations with all 256 threads instead of 64 made the compiler hoist the eight unrolled passes' loads (219 VGPRs spilled, 2.3× slower). |
| Dense IQ2_XXS (shared expert) on the NVFP4 product's WMMA pipeline, group scale folded into BF16 weights | Rejected; 16.7 and 21.6 TFLOP/s against MMQ's 29 TOPS. The fold (F32 product and software BF16 rounding per weight) and four scattered 2-byte loads per 16 values each cost 15–25%; without both 24–28 TFLOP/s, still behind. The shared expert stays on MMQ. |
| Narrower MMQ column tiles for the routed experts (`mmq_x` 16–64 instead of 80) | Rejected; at most 1% faster (48, 64); 24 and 40 are not valid widths. |
| NVFP4 prefill product on FP16 activations written by RMSNorm and the gated norm, 256-token tiles for ssm_in (145 row tiles) | Retained; the product staged F32 activations, 7× the bytes of its weights per block, and converted them per row tile. The norms now store the same F32 value rounded to FP16, so prefill logits stay bit-identical; an empty `asm` keeps the compiler from fusing the last product into `v_fma_mixlo_f16`, which rounds once and broke 11 F32 ties per 151,552 values. Per Mamba layer 15.4 → 12.6 ms (ssm_in 38 TFLOP/s); pp2048 1,087 → 1,154 tok/s, at depth 32K 897 → 945. |
| Other NVFP4 product schedules: grouped row-block order for MALL reuse, 64-value passes, double-buffered LDS with one barrier per pass, loads two passes ahead, real-true16 codegen off, hipBLAS FP16 GEMM on decoded weights | Rejected; −2% to +14% per layer. Double buffering and 64-value passes halved occupancy; hipBLAS reached 5 TFLOP/s on gfx1151. Without true16 the 128 redundant `v_mov_b16`/`v_lshrrev` per pass vanished but the time stayed. |
| Decode concurrent requests in one pass: per-row conv, scan, KV append and attention kernels that read each row's session state through a device table, the matrix products on the stacked rows, one captured graph per width | Retained; rows are bit-identical to decoding each session alone (widths 2, 3 and 8). Sum of decode rates over 8 requests 36.4 (one request) → 138.3 tok/s; llama.cpp with 8 slots 84.4. With the drafter, a lone request drafts and concurrent ones take one token per pass. |
| Zero the values of a verified block's later tokens per row before the P·V WMMA | Retained; their probabilities were already zero, but the WMMA sum rounded differently beside nonzero values, so a verified row differed from decoding its token alone in the last bit and greedy LiLiCorr output left plain decoding at near ties (2 of 8 benchmark depths). The masking touches only the tile holding the query; prefill is unchanged. |
| Short-chunk attention: split z takes key tiles z, z + 64, ... instead of a contiguous share | Retained; the share size depended on the number of keys, so a verified block that crossed 4,096 keys summed in another order than decoding its tokens one by one. |
