# Qwen3.6 35B-A3B experiments

| Experiment | Decision / qualification |
| --- | --- |
| Prefill attention templated on head shape | Retained: the fast prefill kernel was previously compiled only for the Qwen3.8 27B head shape, so this 16Q/2KV `head_dim` 256 model silently fell back to baseline (301 t/s at pp8192) and hit an illegal-memory access at pp16384. Templating on the accepted head shapes restores the fast path. |
| Baseline prefill attention at ≥16K depth | Unresolved: the baseline prefill path crashes at 16384 and above and reproduces with any head shape absent from `detail/attention_policy.hpp`. Out of scope for this model; the accepted-shape fast path must be used instead. |
| MoE share of prefill | Before the attention templating, zeroing the expert output put routed + shared MoE at ~25% of prefill time at 8K depth. After it, per-stage event timing puts MoE at 52% of Q8_K_XL prefill at pp512 and 37% at pp4096 (43% for Q6_K_XL at pp4096); within it, the routed gate/up and down projections dominate. |
| Grouped BF16 expert GEMM (prefill) | Retained: the per-slot GEMV fallback made the 4 BF16 expert layers 29-33% of prefill time (48 ms/layer vs 5 ms/layer for Q8_0 layers at pp512). Grouping slots by expert and running a BF16 WMMA GEMM took Q8_K_XL prefill from 758/885/884 to 1208/1552/1605 t/s at pp512/2048/4096. Activations are rounded to BF16 (as llama.cpp does for BF16 weights); the op-test relative error against the FP32-activation GEMV is 0.13-0.18%. |
| Routed MMQ grid bound | Retained: capping the routed MMQ grid at the chunk's token count gives +7.6-10.1% prefill (Q8_K_XL pp512 1204→1295, pp4096 1601→1728; Q6_K_XL pp512 1221→1318, pp4096 1826→2010). Flash-Next's fitted column tile width on top was rejected: no gain at pp4096, unstable at pp512. |
| BF16 dense projections on the WMMA GEMM (MoE only) | Retained: UD-Q8_K_XL keeps layer 1's `attn_qkv`, `attn_gate` and shared expert in BF16, which the exact FP32-activation route ran at about 1 TFLOPS, doubling GDN input projection time versus UD-Q6_K_XL (22.7% vs 13.5% of a 4K prefill). Prefill chunks of >= 128 tokens now use the BF16 WMMA GEMM: interleaved A/B pp1024 1549 → 1753, pp4096 1716 → 2036, pp16384 1612 → 1872 t/s. Dense Qwen keeps the exact route because its cold/live continuation logits must match exactly. |
| Routed experts on the dense W8A8 WMMA kernel (grouped mode) | Rejected: slots grouped by expert into 16-token-aligned segments, gathered into the tiled Q8_1 layout and run through the dense prefill W-quant x A8 kernel with 32/64/128-token windows. Exact enough (0.4% RMS vs the FP32-activation GEMV, both quants pass the target test) but slower than the routed MMQ route: Q8_K_XL pp4096 2025 → 1744, pp16384 1875 → 1634; Q6_K_XL pp4096 1999 → 1800 t/s. The dense kernel's 29-45 TOPS on the GDN projections comes from reusing each weight tile across the whole chunk; an expert sees ~128 uneven rows at 4K, where its 128-row tiles and deep pipeline are mostly prologue and padding. Code kept outside the tree for reference. |
| Routed Q8_0 experts on Flash-Next's F16 expert GEMM | Retained: slots compacted by expert into 16-row padded buckets from per-expert counts read back once per layer, (expert, token tile) maps of 16 or 48 rows, F16 token rows, and the Flash-Next runner's F16 WMMA GEMM with in-kernel Q8_0 decode (gate, then up with SwiGLU to F16, then down to F16, F16 combine). Interleaved A/B on UD-Q8_K_XL: pp1024 1808 → 2033, pp2048 1966 → 2206, pp4096 2045 → 2251, pp16384 1886 → 2062 t/s; tg unchanged. The op test agrees with the FP32-activation GEMV to ~3e-4 relative (the int8 MMQ route was ~4e-3). UD-Q6_K_XL keeps MMQ (Q6_K gate/up is not decoded by that kernel). The kernels moved into `gufo_qwen38_flash_next_kernels` with unchanged compile flags; Flash-Next pp2048/tg16 is identical before and after. |
| Q6_K decode in the routed F16 expert GEMM | Retained: the kernel assembles each K block's 6-bit codes (ql nibble + qh bits) into bytes at fetch time and stages it like Q8_0, with a (d * scale) pair per 16-element half and the -32 code offset folded into the F16 magic constant (1056). UD-Q6_K_XL now takes the routed path in every layer. Interleaved A/B: pp512 1315 → 1775, pp1024 1694 → 2182, pp2048 1908 → 2384, pp4096 2019 → 2441, pp16384 1861 → 2217 t/s. The op test (random Q6_K blocks against the per-slot GEMV's independent Q6_K decode) agrees to ~4e-4 relative; UD-Q8_K_XL and Flash-Next are unchanged. |
| Paired routed gate/up for Q6_K and Q8_0 | Retained: chunks of >= 1024 tokens run gate and up as one launch over a second 64- or 128-row tile map (the wider one when it launches at most three quarters as many tiles), with SwiGLU in the epilogue and the gate never written, as Flash-Next does for Q4_K/Q5_K. Interleaved A/B, two rounds: UD-Q6_K_XL pp2048 2386 → 2594, pp4096 2434 → 2684, pp16384 2218 → 2411; UD-Q8_K_XL pp2048 2207 → 2316, pp4096 2250 → 2379, pp16384 2057 → 2166 t/s. The op test agrees with silu(gate) * up from two per-slot GEMVs to ~5e-4 relative. |
| Per-projection routed expert routes (prefill MMQ removed) | Retained as a simplification: each routed projection picks its route by its own format, so UD-Q8_K_XL layers 34/38/39 (Q8_0 gate/up, BF16 down) run gate/up on the routed F16 GEMM (F32 rows, separate SwiGLU, since the kernel applies SwiGLU only to F16 output) and down on the grouped BF16 GEMM; the prefill MMQ expert calls and their grid hint are gone (decode keeps the MMQ vector kernels). Both quants pass the op and target tests. Interleaved A/B, two rounds on UD-Q8_K_XL: pp2048 2319 → 2307, pp4096 2385 → 2370, pp16384 2164 → 2158 t/s, tg128 51.6 → 51.8; UD-Q6_K_XL, whose code path is unchanged, moved by the same ~0.5% (pp4096 2692 → 2675), so the difference is within run-to-run noise. |
| Concurrent verification rows sliced to 8 | Retained (fix): with two or more concurrent DFlash2 requests, `ForwardVerificationBatch` stacked up to 8 rows per session into the Q8_0 gated vector kernel, whose row limit is 8, and every such request failed with HTTP 500 ("MoE gated expert projection failed"). The rows are independent, so the launch is sliced into 8-row groups; `qwen35ba3b_target_test` checks 23 stacked rows against per-session references. |
| Concurrent draft cap | Retained: batched verification cost grows with every stacked row, so 7-token drafts for several sessions were slower in total than no drafting (4 concurrent: 88.7 t/s whole-request vs 109.2 without drafts). Fixed draft lengths at 2 and 4 concurrent sessions sized the cap to 3 / 2 / 1 tokens for 2 / 3 / 4+ active requests: 2 concurrent 60.1 → 78.3, 4 concurrent 88.7 → 106.1 t/s whole-request; a lone request keeps the full adaptive draft. |
| Draft cap 0 at 4+ requests | Rejected: a zero-draft step still captures target features for the draft and loses the ~0.6 accepted token per step that a 1-token draft adds; 4 concurrent requests fell from 102.1 to 93.9 t/s whole-request, and 6-8 were unchanged. |
| DFlash2 context injection on the BF16 WMMA GEMM | Retained (MoE targets): profiling showed the target prefill costs the same with and without DFlash2; the whole gap was the draft's context injection, whose `fc`/`attn_k`/`attn_v` matrices are repacked to BF16 at load and ran the exact route 16 rows at a time, ~304 ms per 4K prefill chunk. Injections of 128+ rows now use `LaunchBf16WmmaGemm`, ~45 ms per chunk: single-request prefill 1451/1871/2104/2076 → 1752/2357/2521/2386 t/s at 0.5K/1.6K/6.4K/16K. Greedy long-prompt outputs and draft/accepted counts are unchanged. An earlier attempt keyed on the GGUF's Q8_0 type never ran because of the repacking. |
| Batched verification on the routed F16 expert GEMM | Rejected: routed experts of a verification batch on Flash-Next's routed GEMM with a fixed on-device tile map (no host round trip) and an early exit for empty tiles. Per-step expert time 5.4/29.5/52.5/97.0 ms at 1/8/16/32 rows on the vector kernels vs 8.2/36.3/53.7/78.1 routed. Each row reads 8 of 256 experts, so 8 rows touch ~22% of the 29 GB of expert weights (~33 ms at 200 GB/s) and 32 rows ~64% (~93 ms): the vector kernels already sit at that floor, and the routed GEMM only wins at 32 rows, which the draft cap never produces. The same bound is why speculation stops paying under concurrency on this model. |
| Remaining DFlash2 injection per prefill chunk | Not pursued: each prefill chunk still injects its last 2048 rows although only the final window survives; after the WMMA change that is ~45 ms per extra 4K chunk, about 2% of a long prefill. |
| Cross-session prefill batching | Measured, not built: one 4096-token prompt prefilled in 256/512/1024/2048/4096-token chunks runs at 1193/1830/2314/2605/2707 t/s, because every chunk streams each layer's experts once (~150 ms at 512 tokens). Stacking concurrent sessions' chunks would pay that once: about +26% for 2×512-token prompts, +42% for 4×512, +17% for 4×1024 and nothing measurable from 2K up. `--prefill-chunk 1024` recovers part of it for prompts that arrive while others decode. |
